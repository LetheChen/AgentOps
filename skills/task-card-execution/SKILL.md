# 任务卡片执行与信息完善

> 本 skill 教你（Agent）如何执行任务卡片任务、完善任务信息（依赖关系/子任务/文档关联）、
> 以及在被用户 @ 之后生成有依据的评论回复。
> 核心原则：**数据全部来自工具查询，不臆造；只建议不推进状态。**

---

## 一、标准动作序列（六步，强制顺序）

```
1. 读任务卡 → 2. 查关系 → 3. 查文档 → 4. 装配上下文 → 5. 生成回复/建议 → 6. 落评论
```

### 1.1 第一步：读任务卡

用任务工具读取任务完整信息（必须先拿到这些字段再往下走）：

- 基础：`title` / `description` / `status` / `risk_level` / `task_type`
- 执行：`style_id` / `terminal_session_id` / `assignee_name` / `thread_id`
- 结构：`parent_task_id`（父任务）/ `version`（乐观锁版本，推进时必带）

> 注意：`status` 决定你能做什么——终态（closed/canceled/abandoned）任务只可回顾不可执行。

### 1.2 第二步：查依赖关系（一层即可）

查询当前任务的直接关系，**不要递归多层**：

- **父任务**：`parent_task_id` 指向的任务（读其标题/状态）
- **子任务**：relation_type=`parent_child` 且 source=当前任务的 target 列表
- **上游阻断**（blocked_by）：当前任务被哪些任务阻塞
- **下游阻断**（blocks）：当前任务阻塞了哪些任务

判断逻辑：
- 存在未完成（非 closed）的上游阻断任务 → 当前任务应处于 blocked，执行建议=先完成上游
- 上游全部完成但任务仍 blocked → 建议**解锁**（这是最常见的高价值发现）

### 1.3 第三步：查关联文档索引

查询项目文档列表（设计文档/需求文档/技术方案），找与任务相关的文档：

- 按 task_id 关联的文档提案（doc_change_proposals）优先
- 按标题/描述关键词匹配项目文档（design docs）
- 文档正文是 md 文件，需要时读取文件内容，不要凭记忆复述

### 1.4 第四步：装配上下文

把前三步的结果组装成回复素材：

| 素材 | 用途 |
|------|------|
| 任务卡字段 | 现状陈述（客观） |
| 关系数据 | 依赖分析（可执行/被阻塞/可解锁） |
| 文档索引 | 方案参考（引用文档名，不编造内容） |
| 最近 20 条评论 | 对话上下文（用户 @ 你时的问题背景） |

### 1.5 第五步：生成回复

**回复模板结构**（按序输出）：

```
【任务现状】一句话：标识符 · 标题 · 状态 · 风险
【依赖分析】上游 X 个（其中未完成 Y 个）/ 子任务 Z 个 / 阻塞下游 W 个
【文档参考】关联文档列表（无则写"暂无关联文档"）
【建议】按优先级 1-3 条，每条注明依据（哪个字段/哪条关系/哪份文档）
【下一步】明确"需要你确认"的动作（推进状态/补充信息/解除阻塞）
```

**禁止事项**：
- 禁止直接推进任务状态（advance/rollback/close 需要 requires_user，必须用户操作或明确确认）
- 禁止编造任务字段值、文档内容、不存在的依赖关系
- 禁止超过当前任务一层的关系展开（多层分析问用户要不要做）

### 1.6 第六步：落评论

回复写入任务评论（author_type=agent），格式紧凑：
- 每段一行，用【】分段标题
- 建议条目带编号
- 涉及其他任务用 `标识符·标题` 格式引用

## 二、被 @ 场景（评论区交互）

用户在任务详情页评论区 @ 你（如 `@coding_agent 这个任务怎么执行？`）时：

1. **先跑完整六步序列**（不是只看评论字面意思）
2. 回复必须包含任务真实数据（读卡+查关系的结果），不能只回方法论
3. 用户问执行 → 给执行建议 + 前置条件检查结果（依赖是否就绪）
4. 用户问拆解 → 基于任务描述给出子任务划分建议（只建议，不创建）
5. 用户问方案 → 引用关联文档相关章节（读了才引用）

## 三、完善任务信息场景

用户让你"完善任务信息"时的检查清单：

| 检查项 | 缺失时动作 |
|--------|-----------|
| description 为空或过短 | 建议用户补充，或基于标题+评论生成描述草稿供确认 |
| 无子任务但描述含多个交付点 | 建议拆分子任务（列出建议的子任务标题） |
| 明显的前后依赖但无关系记录 | 建议添加 blocks/parent_child 关系（指明方向和依据） |
| 无关联文档 | 搜索项目文档，建议关联（给出匹配理由） |
| risk_level 与描述复杂度不符 | 建议调整并说明理由 |

所有"建议"都以评论形式输出，**不直接写库**——用户确认后由用户或带确认的流程执行。

## 四、执行编码场景

用户点「执行编码」或让你执行任务时：

1. 前置检查：状态是否允许（in_progress 优先）、依赖是否就绪、风险等级
2. 执行走 `execute_coding` 路径（绑 terminal + workspace，Coding 终端页可观测）
3. 执行过程产出（报告/交付物）落库后，在评论中总结
4. 执行失败 → 报告失败原因 + 三级回退建议（对应任务状态机的 rollback 语义）

---

## 附：数据边界（防幻觉速查）

- 任务字段 → 只有读到的字段才可引用
- 依赖关系 → 只有查询返回的才存在，"看起来像有依赖"不算
- 文档内容 → 只有读过的段落才可引用，其余只引用标题
- 时间 → 用工具返回的时间戳，不用自己的估计
